# Fixture Generator — Implementation Roadmap

**Status:** Planned for v0.1
**Pinned to:** Permit Spec v1.0.0 + test-vectors version 0.1.0-draft
**Last reviewed:** 2026-05-10

This document is the implementation roadmap for the v0.1 fixture generator: architecture, scope, non-goals, module breakdown, risks, and open decisions. It describes what needs to be built so that any contributor — internal or external — can pick this up and execute against a tight specification.

---

## 1. Foundational principle

**Committed fixture bytes are the conformance product. The generator is a reproducibility tool, not the source of truth.**

The bytes in `test-vectors/vectors/*/input/` are what external verifier implementers consume. They are reviewable in PRs. They are byte-comparable in CI. They are the artifact a customer can inspect when evaluating verifier conformance.

The generator's job is **reproducibility**: when the spec evolves or a vector is added, the generator regenerates the affected fixtures deterministically from source.

The generator MUST NOT be a runtime dependency for using the test vectors. An external implementer must be able to run their verifier against the committed bytes without running the generator at all.

## 2. Scope

**In scope for v0.1 — the 9 MVP vectors per `MANIFEST.json` `version_milestones.v0.1`:**

| ID | Category | Failure layer |
|---|---|---|
| `01-01-valid-permit-export` | baseline | (none — PASS) |
| `02-01-record-hash-modified` | tamper-chain | `chain_record_hash` |
| `02-04-sequence-gap` | tamper-chain | `chain_sequence` |
| `03-01-signature-byte-flipped` | tamper-signature | `manifest_signature` |
| `04-01-dispatch-digest-mismatch` | closure-binding | `closure_dispatch_binding` |
| `05-01-key-reorder-equivalent` | canonicalization | (none — PASS-equal) |
| `05-02-non-canonical-similar` | canonicalization | (none — PASS-different) |
| `06-01-retired-key-still-verifies` | key-rotation | (none — PASS with retired key) |
| `07-01-empty-bundle` | bundle-format | (none — PASS edge case) |

Each fixture must be:

- Generated by a deterministic recipe.
- Self-consistent (manifest hash matches actual bytes; manifest signature verifies; all layers OTHER than the deliberately-invalid one are valid).
- Byte-identical across Linux, macOS, and Windows runners.
- Reproducible: re-running the generator on the same source MUST produce identical bytes.

## 3. Non-goals (explicit out-of-scope for v0.1)

| Non-goal | Rationale |
|---|---|
| **Full 31-vector population** | v0.1 is the smoke-test minimum. Populating the remaining 22 vectors is v1.0 work. |
| **Dependency on the reference implementation's private code** | The fixture core MUST live entirely under `test-vectors/tools/lib/` with public, spec-pinned implementations of canonicalization, signing, chain, and manifest assembly. External implementers will not have access to the reference implementation's private code. |
| **Dynamic fixtures (CI regenerates fresh each time)** | Fixtures are committed. CI regenerates into a temp dir and byte-compares against committed bytes. "Always regenerate" hides meaningful fixture changes in CI behavior. |
| **Schema validation of `expected.json`** | Out of scope for v0.1. JSON Schema for `expected.json` per `CONFORMANCE.md` is a follow-up if it becomes load-bearing. |
| **Full conformance runner CLI** (`keel-conformance run --verifier X --vectors Y`) | Separate deliverable. Spec lands alongside v0.1 fixtures; CLI ships post-v0.1. |
| **Production test keys** | Test keys are clearly marked `environment: "test"` and `key_id` prefixed with `keel-test-`. They are committed publicly. A production verifier MUST reject test-key signatures regardless of cryptographic validity. |
| **Non-LF line endings** | Forced by `.gitattributes`. Generator MUST produce LF-only output regardless of platform. |
| **UUIDv4 randomness** | Test vectors should read like legal exhibits, not random output. Use fixed semantic IDs (e.g., `permit-01-01-baseline`, `chain-02-01-seq2-tampered`) unless the vector specifically tests UUID handling. |

## 4. Architecture

```
test-vectors/
├── tools/
│   ├── IMPLEMENTATION.md             (this file)
│   ├── generate_fixtures.py          (entry-point CLI)
│   ├── check_fixtures.py             (byte-compare CI mode)
│   ├── lib/
│   │   ├── __init__.py
│   │   ├── canonical_json.py         (deterministic canonicalization pinned to spec v1.0.0)
│   │   ├── chain.py                  (record-hash + prev-hash computation)
│   │   ├── permit.py                 (Permit object construction)
│   │   ├── closure.py                (closure_v2 record construction + binding digests)
│   │   ├── manifest.py               (audit-export-bundle manifest assembly)
│   │   ├── signing.py                (Ed25519 raw 32-byte signing)
│   │   ├── tamper.py                 (deterministic tamper recipes per vector)
│   │   └── verify_self_check.py      (invoke keel-verifier against generated output before commit)
│   └── test-keys/
│       ├── README.md                 (key generation procedure + rotation policy)
│       ├── export-signing-test.priv  (raw 32-byte Ed25519 private key, base64)
│       ├── export-signing-test.pub   (raw 32-byte Ed25519 public key, base64)
│       └── trust-root-test.json      (test trust root manifest for fixtures)
```

### 4.1 Public spec-pinned fixture core (`tools/lib/`)

Each module under `lib/` implements one orthogonal piece of fixture generation. Module versions track the Permit Spec version they target.

| Module | What it does | Spec reference |
|---|---|---|
| `canonical_json.py` | Deterministic JSON serialization. Sorts keys lexicographically, no whitespace, UTF-8 without BOM, escape sequences per spec. | `spec/canonical-json.md` |
| `chain.py` | Computes `record_hash = sha256(canonical_bytes_of_entry_content)`, threads `prev_hash` from previous entry's `record_hash`. Genesis entry has `prev_hash = sha256("permit-spec-genesis-v1")` or whatever the spec specifies. | `spec/chain-entry.md` |
| `permit.py` | Constructs Permit objects from semantic field values. Permit IDs are fixed strings (not UUIDs) for v0.1 fixtures to keep them human-readable. | `spec/permit-v1.md` |
| `closure.py` | Constructs `closure_v2` records with dispatch / provider / client digest fields. For tamper fixtures, supports surgically substituting one digest while keeping others coherent. | `spec/closure-v2.md` |
| `manifest.py` | Assembles audit-export-bundle manifest with `content_hash` over actual export bytes. Recomputes after tampering. | `spec/audit-export-bundle.md` |
| `signing.py` | Loads raw 32-byte Ed25519 private key from `test-keys/`, signs canonical manifest bytes. Output is 64-byte raw signature, NOT base64 or DER. | `spec/audit-export-bundle.md` §9 |
| `tamper.py` | Each MVP tamper vector has a `def tamper_<id>(golden_bundle) -> tampered_bundle` function. Encodes the exact mutation recipe documented in each vector's `description.md`. | per-vector description.md |
| `verify_self_check.py` | After generating output, invokes the reference verifier (`keel-verifier` from PyPI) against the temp output and compares against `expected.json`. Refuses to commit if the verifier output doesn't match the vector's expectation. | `CONFORMANCE.md` |

### 4.2 Determinism contract

All of the following MUST be stable across runs and across platforms:

- File byte order within a tar/zip: out-of-scope for v0.1 (no archived bundles in MVP fixtures).
- JSON key order: lexicographic per `canonical_json.py`.
- JSON whitespace: none (compact serialization).
- File line endings: LF only (`.gitattributes` enforces this end-to-end).
- File trailing newline: present, exactly one byte (`\n`).
- Timestamps in fixtures: hardcoded constant per fixture (e.g., `2026-05-10T00:00:00Z`). Never wall-clock time.
- UUIDs / IDs: fixed semantic strings, not random.
- Ed25519 signatures: deterministic by construction (the signing algorithm is deterministic given key + message — but library output formats vary; `signing.py` enforces raw 64-byte output).
- Public key encoding: raw 32 bytes, base64-encoded with `=` padding.

If a single byte differs between two generator runs on the same source, the generator has a determinism bug. CI catches this via the byte-compare mode.

### 4.3 Atomic write protocol

To prevent partially-written fixtures from polluting the committed state:

1. Generator writes to `test-vectors/tools/.tmp/<vector_id>/` (gitignored).
2. After write, runs `verify_self_check.py` against the temp output.
3. If self-check matches `expected.json`, atomically moves temp dir contents to `test-vectors/vectors/<vector_id>/input/`.
4. If self-check fails, fails loudly and leaves `.tmp/` for inspection. Does NOT touch the committed `input/` directory.

The byte-compare CI mode is the inverse: generate to `.tmp/`, compare against committed `input/`, fail if any byte differs.

### 4.4 Per-artifact SHA-256 manifest

After successful generation, the generator updates the `artifact_hashes` field in the vector's `expected.json` with the SHA-256 of each written file. This is the fixture-local cross-platform tripwire described in `CONFORMANCE.md`.

Until v0.1 ships, `artifact_hashes` values are `sha256:TBD-generator-pending`. The generator's first successful run replaces those with real hashes; CI then enforces byte-identity on subsequent runs.

## 5. CLI

Single Python entry point at `test-vectors/tools/generate_fixtures.py`. Three subcommands.

### 5.1 `generate-one`

```
python tools/generate_fixtures.py generate-one --vector-id cat-01-baseline/01-01-valid-permit-export
```

Generates exactly one vector. Useful for development. Atomic-write protocol applies. Updates `artifact_hashes` in that vector's `expected.json`.

### 5.2 `generate-mvp`

```
python tools/generate_fixtures.py generate-mvp
```

Generates all 9 MVP vectors sequentially. Stops on first failure. Useful for full regeneration after a spec-pinned canonicalization change.

### 5.3 `check`

```
python tools/generate_fixtures.py check
```

Byte-compare mode for CI. Regenerates into `.tmp/`, compares byte-for-byte against committed `input/`. Exits non-zero on any difference. Reports which file in which vector diverged.

### 5.4 Optional flags

- `--vector-id <id>` — explicit single-vector targeting (with `generate-one` and `check`)
- `--out-dir <path>` — override default `vectors/<id>/input/` destination (for testing)
- `--skip-verifier-self-check` — for bootstrap when keel-verifier isn't installed yet. Logs warning. Should NOT be used in CI.
- `--allow-overwrite` — required to replace existing non-placeholder fixtures. Bare `generate-one` refuses if real bytes exist.

## 6. Implementation sequencing

The work decomposes into three sequential phases.

### Phase 1 — Bootstrap milestone (single-vector golden path)

Before any tamper vector is touched:

1. Implement `canonical_json.py`, `permit.py`, `chain.py`, `manifest.py`, `signing.py` modules. Each module independently tested against its spec section.
2. Generate test keys, commit `tools/test-keys/`. Public key format: raw 32-byte base64 with `environment: "test"` + `key_id: "keel-test-export-signing-v1"` in the trust-root JSON.
3. Implement `generate-one` subcommand sufficient to produce `01-01-valid-permit-export`.
4. Implement `verify_self_check.py` invoking `keel-verifier` against the temp output.
5. Run `generate-one --vector-id cat-01-baseline/01-01-valid-permit-export` three times in succession. **All three runs MUST produce byte-identical output across all 5 files in `input/`.** This is the determinism gate.
6. Commit the resulting fixtures. `expected.json` `artifact_hashes` now contains real SHA-256 values.

After Phase 1:
- The fixture core's determinism is proven.
- The CI byte-compare gate has a real reference to test against.
- The signing flow + key format is locked.
- Subsequent vectors (especially tampers) reuse the same plumbing.

This phase is the foundational one because every architectural choice (signing format, canonicalization, trust-root structure, file naming) gets locked in by the bytes that ship in this single fixture. Phase 1 done right means the remaining 8 vectors compose against a stable base.

### Phase 2 — MVP vector population

After Phase 1 lands:

1. Implement the remaining 8 MVP vectors using `tamper.py` recipes. Tamper vectors share the Phase 1 golden bundle as a starting point; each applies a deliberate mutation and recomputes downstream hashes that should remain valid.
2. Implement `generate-mvp` subcommand to drive all 9 vectors in sequence.
3. Each vector's `expected.json` `artifact_hashes` field is populated by the generator on first successful run.

### Phase 3 — CI integration

After Phase 2 lands:

1. Implement `check_fixtures.py` byte-compare gate.
2. Wire into CI workflow that runs on every push touching `test-vectors/`.
3. Include at least one Windows runner in the CI matrix (verifies LF line-ending enforcement end-to-end).

## 7. Risks

### 7.1 Schema drift

**Risk:** the generator's understanding of Permit Spec drifts from the spec text. Generator produces fixtures that pass the reference verifier but fail third-party verifiers that read the spec correctly.

**Mitigation:**
- `canonical_json.py` is implemented from spec text, NOT from the reference implementation's code.
- Every fixture's `expected.json` carries `spec_version: "permit-v1.0.0"`. If spec evolves, fixtures must be regenerated against the new version into a separate directory (`test-vectors/v1.1.0/` rather than overwriting `v0.1.0`).
- Lock `generator_version` in fixture manifests once implemented; allows tracing back which generator produced which committed fixture.

### 7.2 Newline drift

**Risk:** Windows runner produces CRLF instead of LF; SHA-256 computations diverge across platforms.

**Mitigation:**
- `.gitattributes` enforces LF on text files.
- Generator MUST write files with explicit `\n` newlines, NOT `os.linesep`.
- CI runs on at least one Windows runner to catch any newline regressions.

### 7.3 Error precedence ambiguity

**Risk:** External verifier processes vector 02-04 differently — checks chain linkage before sequence monotonicity, reports `WALK_PREV_HASH_DISCONTINUITY` before `WALK_SEQUENCE_INVERSION`. Both verifiers are "right" by some reading.

**Mitigation:**
- Per-vector `expected.json` documents `primary_failure_code` AND `acceptable_secondary_codes`. If a code is acceptable, the spec must enumerate it explicitly.
- For 02-04 specifically: the fixture is constructed so the chain linkage is also broken at the gap (entry 5 → entry 7's prev_hash cannot be entry 5's record_hash). Verifier may emit either `WALK_PREV_HASH_DISCONTINUITY` or `WALK_SEQUENCE_INVERSION`; `expected.json` MUST list the non-primary code under `acceptable_secondary_codes`.

### 7.4 Spec version skew

**Risk:** Permit Spec v1.0.0 fixtures are regenerated with a v1.0.1 generator (e.g., after a canonicalization tightening), and the bytes drift even though the spec change was supposed to be backwards-compatible.

**Mitigation:**
- Generator version pinning. `tools/lib/__init__.py` declares `__permit_spec_version__ = "1.0.0"`. Any spec change above this requires a new generator version.
- v1.0 → v1.1 spec change creates `test-vectors/v1.1.0/` alongside `v0.1.0/`. Existing fixtures are not regenerated. Customers can run against either version.

### 7.5 Over-isolated tampering

**Risk:** Every tamper vector is re-signed-after-tamper, so external implementers learn to expect "valid signature, invalid chain." A real attacker who can't re-sign produces "invalid signature, no deeper check needed" bundles, which verifiers never see in test fixtures.

**Mitigation:**
- v0.1 MVP already includes both classes: `03-01-signature-byte-flipped` invalidates the manifest signature without re-signing. `02-01-record-hash-modified` keeps the signature valid.
- Per-vector `description.md` documents which class the fixture exercises.
- v1.0 expansion adds more fixtures of each class.

### 7.6 Test key compromise / confusion

**Risk:** Test keys leak. Or production verifier accidentally accepts test-key signatures.

**Mitigation:**
- Test keys are NOT secret; they are committed publicly. There is no "compromise" because there is no trust to compromise — production verifier rejects them by `key_id` prefix (`keel-test-*`) and `environment: "test"` field.
- Production verifier conformance MUST include a fixture proving it rejects test-key signatures even when cryptographically valid. (This is itself a future vector: `cat-08-test-key-confusion`, post-v0.1.)
- Test keys are rotated only when test vectors are regenerated. Rotation cadence: yearly or on Permit Spec major version bump.

### 7.7 Verifier circular dependency

**Risk:** The generator's self-check uses `keel-verifier`. If `keel-verifier` has a bug that masks a generator bug, the bug ships in the fixtures.

**Mitigation:**
- Self-check is one of TWO validation steps. The other is structural lint: independent recomputation of hashes from canonical bytes, independent signature verification using a different Ed25519 library implementation if available.
- For v0.1: structural lint MAY be lightweight (recompute manifest content_hash, check signature non-emptiness, validate JSON parse). A more thorough independent-verifier check is v1.0 work.

## 8. Open decisions for the implementer

These choices are deliberately deferred. The implementation contributor makes them based on what works in practice; any one of them could be revisited later without breaking v0.1.

1. **Python version target.** 3.11+ recommended for `tomllib`, structural pattern matching, and consistent JSON handling. Could be 3.10 if external implementers need it; consult before deciding.

2. **Ed25519 library.** PyNaCl, cryptography (Python `cryptography` package), or hand-rolled `pyca/cryptography`. Recommendation: `cryptography` for stability + audit history. NOT PyNaCl's high-level API (encodes in unusual ways).

3. **Fixture timestamp.** Hardcoded `2026-05-10T00:00:00Z` for all v0.1 fixtures, OR per-vector timestamps that semantically reflect the scenario. Recommendation: one shared timestamp for all v0.1 to reduce variation; v1.0 can introduce per-vector timestamps when key-rotation vectors need temporal variety.

4. **Permit ID format.** Semantic strings (e.g., `permit-01-01-baseline-allow`) vs UUIDv4 derived from seed. Recommendation: semantic strings for v0.1 readability; UUIDv4 vectors come in if/when a vector specifically tests UUID handling.

5. **Trust-root JSON format.** Match the existing `keel-verifier` bundled trust root format byte-for-byte. Recommendation: copy the schema from `keel_verifier/data/trust_root.json` and pin a `format_version` field.

6. **Where the generator runs in CI.** A separate workflow file (`generate-test-vectors.yml`) that runs on push to test-vectors paths, OR baked into the main CI pipeline. Recommendation: separate workflow so external contributors can see the gate without scrolling through main CI logs.

7. **Whether the generator imports `keel-verifier` or invokes it as a subprocess.** Subprocess is cleaner isolation; import is faster. Recommendation: subprocess for v0.1 (the generator runs once per fixture; subprocess overhead is negligible).

## 9. Success criteria for v0.1

v0.1 ships when ALL of the following are true:

- [ ] 9 MVP vectors have real bytes committed under `vectors/<id>/input/`.
- [ ] Each MVP vector's `expected.json` `artifact_hashes` contains real SHA-256 values (no `TBD-generator-pending`).
- [ ] Running `python tools/generate_fixtures.py check` from a clean checkout exits 0.
- [ ] Running `keel-verifier` against each MVP fixture produces output that matches the vector's `expected.json` per the matching rules in `CONFORMANCE.md`.
- [ ] CI runs the `check` step on every push that touches `test-vectors/`.
- [ ] At least one CI runner is Windows (verifies LF/newline handling).
- [ ] `tools/test-keys/` contains committed test keys with `environment: "test"` and `keel-test-*` key_ids.
- [ ] `tools/lib/canonical_json.py` has at least one explicit test that two semantically-equivalent JSON inputs (different key order) canonicalize to identical bytes.
- [ ] An external implementer reading this directory + `CONFORMANCE.md` could plausibly write a verifier in another language (Go / Rust / TypeScript) against the spec and known-good fixtures without further questions.
