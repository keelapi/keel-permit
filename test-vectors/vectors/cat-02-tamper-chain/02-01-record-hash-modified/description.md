# 02-01 — Single Chain Entry's `record_hash` Modified

## What this exercises

A conforming verifier MUST detect any modification to a chain entry's `record_hash` field. This is the most basic tamper-evidence property: changing any single byte of any chain entry's hash should fail verification.

Specifically: take a known-good chain segment, modify one byte of the `record_hash` field on the entry at sequence 2, and re-run verification. The verifier MUST:

1. Recompute the expected `record_hash` for sequence 2 from its content.
2. Detect that the stored `record_hash` does not match the recomputed value.
3. Emit failure code `WALK_RECORD_HASH_MISMATCH`.
4. Identify the failure position as `chain_entry` at `sequence: 2`.

This is the failure code shown in the user-facing disappearance demo (`Keel_Demo_Script_2026-05-10.md` beat 4).

## Inputs

- `input/export.jsonl` — chain segment of 5 entries; entry at sequence 2 has its `record_hash` field modified.
- `input/manifest.json` — manifest. Note: the manifest's `content_hash` is the hash of the TAMPERED export, so manifest verification PASSES; only the chain walk fails. (This is the realistic attack — a sophisticated tamperer recomputes the manifest hash after modifying the chain. The chain walk is what catches them.)
- `input/signature.bin` — valid signature over the tampered manifest.
- `input/trust-root.json` — test trust root.

## Expected behavior

A conforming verifier:

- Reports `result: "FAIL"`.
- Reports `failure_codes: ["WALK_RECORD_HASH_MISMATCH"]`.
- Reports `first_failure_at: {"type": "chain_entry", "sequence": 2}`.

A non-conforming verifier might:

- Report `PASS` because it only checked the manifest signature and not the chain.
- Report `FAIL` but with a wrong failure code (e.g., `MANIFEST_HASH_MISMATCH`).
- Report `FAIL` but identify the wrong position (e.g., `sequence: 0` or `sequence: 4`).

## Why this matters

The threat model is: an attacker with access to the audit storage modifies a chain entry to hide an action that should have triggered a denial. If the verifier only checks signatures and not the chain walk, the modification is undetectable. The chain walk is the second layer of defense.

This is the canonical "tamper-evident" test. Every verifier that claims tamper-evidence MUST pass this test.

## Why this is "scaffolded" not "complete"

Same fixture-generator dependency as `01-01-valid-permit-export`. The fixture is described, the expected output is binding, but the actual byte-level export with the single-byte modification needs to be generated by the test-fixture tool when it is committed.

## Tamper construction recipe (for the fixture generator)

When generating this fixture:

1. Start from the `01-01-valid-permit-export` golden bundle.
2. Extend the chain to 5 entries with synthetic governance events.
3. Modify a single byte of the `record_hash` field on entry sequence 2.
4. Recompute the manifest's `content_hash` over the modified bundle.
5. Re-sign the recomputed manifest with the test signing key.
6. Commit the result.

Step 4-5 are critical: the manifest signature MUST still verify, otherwise the test conflates two failure conditions.
